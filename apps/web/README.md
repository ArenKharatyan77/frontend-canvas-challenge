# @canvas/web

Фронтенд для редактора нод: React 19, TypeScript, React Flow (`@xyflow/react`), Vite.

Часть кода написана с помощью Claude AI (Anthropic) — по условиям задания использование нейросетей и помощников для написания кода разрешено.

## Запуск

Бэкенд поднимается отдельно из корня репозитория:

```sh
npm install          # один раз, из корня — поставит зависимости всех workspace
npm run dev           # из корня — API на http://localhost:4001
```

Фронтенд — в соседнем терминале:

```sh
npm run dev -w @canvas/web
```

Откройте `http://localhost:5173`. Пространство создаётся автоматически при первом заходе и запоминается в `localStorage` (`canvas.spaceId`), так что после перезагрузки открывается то же самое.

Если API работает не на 4001, задайте адрес через `.env` (скопируйте `.env.example`):

```
VITE_API_URL=http://localhost:4101
```

## Сборка

```sh
npm run build -w @canvas/web   # проверка типов + сборка в apps/web/dist
npm run preview -w @canvas/web # локальный просмотр собранной версии
```

## Устройство кода

### API-слой (`src/api`)

Всё общение с сервером идёт через `request()` в `src/api/http.ts` — один fetch-обёртчик, который:

- собирает адрес из `VITE_API_URL` и подставляет заголовки (`Content-Type`, `If-Match`, `Idempotency-Key` и т.д.);
- сам проверяет `response.ok`, парсит `error.code`/`error.message` из тела и бросает `ApiError` с готовыми полями;
- различает пустые ответы (`204`) от JSON-тела;
- отдаёт вместе с данными заголовки ответа (`ETag` в первую очередь нужен для графа).

Модули `spaces.ts`, `graph.ts`, `generations.ts`, `config.ts` — тонкие обёртки над `request()` с конкретными путями и типами из `@canvas/contracts`. Ни в одном компоненте нет своего `fetch`, `response.json()` или `catch` — если серверный контракт поменяется, правится один файл, а не поиск по всем местам вызова.

### Сохранение графа (`src/domain/graphSaveQueue.ts`)

`GraphSaveQueue` — небольшой класс без привязки к React, инкапсулирующий весь протокол debounce + ETag:

- `schedule(graph)` откладывает сохранение на `debounceMs` (берётся из `/api/config`), повторные вызовы просто переставляют таймер;
- одновременно может выполняться только один `PUT`; если во время запроса пришли новые правки, они не теряются — сохранятся следующим проходом;
- при `412` (конфликт версии) правки остаются в очереди, наружу сообщается статус `conflict`, а `reload()` перечитывает граф с сервера и сбрасывает ETag;
- `flush()` принудительно дожидается текущего и всех накопившихся сохранений — это то, что вызывается перед стартом генерации, чтобы её запускать по уже сохранённой версии графа.

Хук `useGraphSaveQueue` — просто подписка React-состояния на этот класс (создаётся один раз через `useRef`, эмитит статус через `subscribe`). Сам React ничего не знает про дебаунс и гонки запросов — вся эта логика живёт в одном месте и не размазана по компонентам нод.

### Генерация и опрос статуса (`src/domain/generationTracker.ts`)

`GenerationTracker` устроен аналогично: держит карту «нода генератора → последняя генерация», на каждый запуск создаёт новый `AbortController`, поллит `GET /generations/:id` с интервалом из конфига и сверяет `id` перед тем как записать результат — если за это время была запущена новая генерация той же ноды или нода удалена, устаревший ответ просто отбрасывается. `dispose()` останавливает все опросы при размонтировании страницы.

### Индекс графа и правила связей (`src/domain/graphIndex.ts`, `graphRules.ts`)

`buildGraphIndex(nodes, edges)` — единственное место, которое ходит по массивам `nodes`/`edges`. За один проход по каждому строит три `Map`: `nodesById`, `incomingSource` (вход → откуда пришла связь) и `outgoingTarget` (выход генератора → результат). Всё остальное — проверка допустимости соединения, поиск «есть ли у генератора результат», подстановка картинки в нужную ноду результата — обращается к этим картам за O(1), а не бегает по массиву заново на каждый чих. Правило допустимых связей (`prompt → generator → result`, один вход, один выход у генератора) описано один раз в `isConnectionAllowed` и используется и для `isValidConnection` React Flow, и как источник правды при подсчёте `hasResultTarget`.

### Компоненты и контекст (`src/components`)

`Canvas.tsx` держит состояние `nodes`/`edges` (через `useState` + `applyNodeChanges`/`applyEdgeChanges`, а не `useNodesState`, потому что после каждого изменения нужно тут же собрать persisted-граф и отдать его в очередь сохранения). Ноды (`PromptNode`, `GeneratorNode`, `ResultNode`) не получают колбэки через `data` — вместо этого есть контекст `CanvasActionsContext` с действиями (`updateText`, `deleteNode`, `generate`, ...). Так `node.data` остаётся ровно тем, что уходит на сервер (просто `{ text }` или `{ label }`), и не нужно перед каждым сохранением вычищать оттуда функции и служебные поля React Flow (`selected`, `dragging`, `measured`) — они и так никогда туда не попадают.

## Производительность: один реальный пример

`buildGraphIndex` вызывается в `Canvas.tsx` через `useMemo(() => buildGraphIndex(nodes, edges), [nodes, edges])` — то есть при каждом изменении состава/связей графа (перетаскивание ноды, соединение, удаление, добавление). При максимуме задания — 20 нод и 20 связей — это два линейных прохода (`for (const node of nodes)`, `for (const edge of edges)`), без вложенных обходов и без промежуточных массивов: `nodesById.set`, `incomingSource.set`, `outgoingTarget.set` пишут сразу в целевые `Map`.

Альтернатива, которая была на столе — искать нужные связи через `edges.find(e => e.target === id)` прямо в компонентах `GeneratorNode`/`ResultNode` на каждый рендер каждой ноды. При 20 нодах и 20 связях это до 20 линейных проходов по массиву связей на один рендер канваса вместо одного общего прохода на всех — асимптотика та же O(N·E) против O(N+E), и на таком размере разница не критична, но с ростом графа (а `MAX_NODES`/`MAX_EDGES` — это только ограничение бэкенда для тестового, не архитектурное) она была бы кратной числу нод. Индекс строится один раз на изменение структуры графа и переиспользуется всеми потребителями за один рендер.

Второй момент — точечные обновления не пересоздают весь массив нод. `updateText` в `Canvas.tsx` делает `nodes.map(...)`, заменяя ссылку только у одной ноды:

```ts
current.map((node) =>
  node.id === nodeId && node.type === 'prompt' ? { ...node, data: { ...node.data, text } } : node,
);
```

Остальные 19 объектов нод остаются той же ссылкой, что и до правки — React Flow не будет лишний раз перерисовывать ноды, которые не менялись.

## Проверенные сценарии

- Первый заход создаёт пространство, `spaceId` переживает перезагрузку страницы (граф, связи и позиция канваса восстанавливаются с точностью до координат — сверено напрямую с сохранённым на сервере графом, не только на глаз).
- Добавление всех трёх типов нод, перетаскивание с сохранением позиции, ввод текста, удаление ноды — с каскадным удалением её связей и на клиенте, и в сохранённом на сервере графе.
- Соединение перетаскиванием: `текст → генератор → результат` создаётся, обратные и однотипные связи (`isValidConnection`) отклоняются интерфейсом.
- Автосохранение: серия быстрых правок даёт одно сохранение через 500 мс, бейдж показывает `pending → saving → saved`, `If-Match` уходит с актуальным ETag.
- Лимит в 20 нод: кнопки добавления блокируются по достижении потолка, попытка добавить в обход (принудительный клик по задизейбленной кнопке) не даёт узлу состояния превысить 20 ни на клиенте, ни на сервере.
- Конфликт версии графа: второй клиент сохраняет граф параллельно (напрямую через API), после чего правка в интерфейсе получает `412` — показывается баннер конфликта, локальный черновик не стирается, «Перечитать граф» подтягивает актуальную версию с сервера и снимает конфликт, дальнейшее автосохранение продолжает работать как обычно.
- Полный цикл генерации: нажатие «Сгенерировать» дожидается сохранения графа, показывает «Генерируем…», через задержку из `/api/config` получает картинку и показывает её в связанной ноде результата.
- Двойной клик по «Сгенерировать» не создаёт дублей — кнопка блокируется на время активной генерации, идентификатор ключа новый на каждый настоящий запуск.
- Тестовый отказ: кнопка «Смоделировать отказ» на ноде генератора запускает генерацию со сценарием `failure`, узел показывает состояние ошибки, кнопка превращается в «Повторить».

Всё это прогонялось вручную через Playwright (headless Chromium) поверх реального API, включая прямые запросы к серверу в обход интерфейса для имитации второго клиента и проверки того, что реально сохранилось (не только что показано на экране) — скриптов автотестов в репозитории нет, только ручная/скриптовая проверка перед сдачей.

В процессе этих проверок нашлись и были исправлены два реальных бага:

1. Каскадное удаление ноды с связями срабатывает как два независимых события (`onNodesChange` и `onEdgesChange`) в одном батче React. Каждый обработчик поначалу собирал persisted-граф из своего свежего массива и **чужого** несвежего (замыкание на состояние до обновления) — в результате на сервер могла уйти версия, где связи уже удалены, а нода ещё нет. Исправлено: оба обработчика только выставляют флаг «граф изменился», а один `useEffect` над актуальными `[nodes, edges]` сам решает, когда сохранять — так оба массива в сохранении всегда согласованы между собой.
2. После `reload()` (перечитывание графа после конфликта) вызывается `reactFlowInstance.setViewport(...)`, чтобы синхронизировать раскладку канваса — это само по себе порождает событие `onMoveEnd`, которое запускало лишнее сохранение сразу после перезагрузки. Исправлено сравнением фактического viewport с уже известным (`viewportRef.current`) вместо изначальной попытки погасить событие по таймеру — тайминг оказался ненадёжным (`requestAnimationFrame` не всегда успевал до срабатывания события), а сравнение значений детерминированно и не зависит от таймингов браузера.

## Известные недоработки

- Вёрстка рассчитана на 1280px и шире, мобильная адаптация не делалась (по условиям задания не оценивается).
- React Flow даёт минимальную кастомизацию путей связей «на глаз» — не подбирался кастомный `edgeType`.
- Лимит в 20 связей структурно недостижим через легитимный UI при лимите в 20 нод: правила связности (один вход на ноду, один выход у генератора) требуют 3 узла на 2 связи, то есть максимум 6 полных цепочек = 12 связей при 20 нодах. Код на `MAX_EDGES` всё равно проверяется (`edges.length >= MAX_EDGES` в `handleConnect`/`isValidConnection`), просто сценарий с реальным упором в 20 связей физически не собрать без нарушения других правил.
